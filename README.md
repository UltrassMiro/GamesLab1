Відповіді на контрольні запитання:

1. OOP базується на інкапсуляції, наслідуванні, поліморфізмі та абстракції. Основні проблеми — надмірне наслідування та сильна зв’язаність класів. Рішення — модульність, інтерфейси та SOLID.
2. Абстракція — це приховування деталей реалізації та виділення головних характеристик. Вона спрощує проектування та зменшує залежності між модулями.
3. Single Responsibility означає, що клас повинен виконувати лише одну задачу. Проблема виникає, коли клас має багато обов’язків. Рішення — розділення логіки на окремі класи.
4. Open-Closed означає, що код має бути відкритим для розширення, але закритим для зміни. Для цього використовують інтерфейси, абстрактні класи та поліморфізм.
5. Liskov Substitution означає, що дочірній клас повинен коректно замінювати базовий. Проблеми виникають при неправильному наслідуванні. Рішення — правильна ієрархія або композиція.
6. Interface Segregation означає, що не слід створювати великі універсальні інтерфейси. Краще використовувати кілька вузьких інтерфейсів.
7. Dependency Inversion означає, що модулі повинні залежати від абстракцій, а не від конкретної реалізації. Це зменшує зв’язаність системи.
8. Абстрактний клас може містити реалізовані методи та поля. Інтерфейс описує лише поведінку. Абстрактний клас — для спільної логіки, інтерфейс — для контракту.
9. DRY — уникнення дублювання коду. YAGNI — не реалізовувати зайвий функціонал. KISS — робити систему простою. Ці принципи спрощують підтримку програми.
10. Cohesion — зв’язність елементів всередині модуля, coupling — залежність між модулями. Хороша система має високу cohesion і низький coupling.
11. Наслідування використовують для відношення “is-a”, композицію — для “has-a”. Композиція гнучкіша та безпечніша.
12. При проектуванні ПЗ потрібно враховувати масштабованість, підтримуваність, безпеку, залежності між модулями та зберігання даних.
13. Основні практики: SOLID, DRY, KISS, YAGNI, модульність, тестування, рефакторинг та code review.
14. Code standards та conventions потрібні для єдиного стилю коду та полегшення підтримки. Для C# використовують Microsoft Coding Conventions.
15. Duck Behavior означає, що важливий не тип об’єкта, а його поведінка. Якщо об’єкт має потрібні методи — його можна використовувати.
